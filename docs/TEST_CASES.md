# 냉장고 구조대 테스트 케이스

## 1. 목적

이 문서는 제품 요구사항과 예외처리가 실제 구현 및 검증에서 빠지지 않도록 관리하는 살아 있는 테스트 명세다.

- 기능 구현과 테스트 코드를 같은 작업 단위에서 작성한다.
- 각 테스트는 제품 요구사항 `FR-*` 또는 예외처리 ID를 연결한다.
- P0 비즈니스 규칙은 단위 테스트로 먼저 고정한다.
- 사용자의 핵심 여정은 Compose UI 또는 계측 테스트로 검증한다.
- 자동화하기 어려운 접근성·기기 동작은 수동 QA 결과를 남긴다.

## 2. 상태와 우선순위

### 상태

| 상태 | 의미 |
|---|---|
| `PLANNED` | 케이스만 정의되었으며 아직 구현되지 않음 |
| `AUTOMATED` | 자동 테스트 코드가 작성되어 로컬·CI에서 실행됨 |
| `MANUAL` | 수동 검증 대상으로 준비됨 |
| `PASSED` | 대상 빌드에서 통과함 |
| `FAILED` | 결함이 확인되었으며 이슈 연결이 필요함 |
| `BLOCKED` | 환경이나 선행 기능 부족으로 실행할 수 없음 |

### 우선순위

| 우선순위 | 기준 |
|---|---|
| `P0` | 데이터 유실, 잘못된 자동 처리, 핵심 여정 중단, 개인정보 노출 가능성 |
| `P1` | 우회 가능하지만 주요 사용성이나 신뢰에 영향을 줌 |
| `P2` | 완성도, 성능 최적화, 후속 범위 |

아래 자동화 현황에 포함되지 않은 케이스는 `PLANNED`다.

## 14. 핵심 사용자 여정 인수 테스트

### `AT-001` 온라인 주문 텍스트 공유부터 저장

1. 온라인 마트 주문내역 텍스트를 앱으로 공유한다.
2. 품목 추출이 끝날 때까지 기다린다.
3. 자동 후보, 확인 필요, 제외 수를 확인한다.
4. 후보 하나를 해제하고 확인 필요 하나를 포함한다.
5. 일괄 저장한다.

기대 결과:

- 공유 시작부터 저장까지 앱 내에서 흐름이 끊기지 않는다.
- 사용자가 마지막으로 선택한 품목만 Room에 저장된다.
- 제조사 날짜와 예상 날짜의 근거가 구분된다.
- 같은 입력을 다시 공유하면 자동 중복 저장하지 않는다.

### `AT-002` 오늘의 구조에서 소비하고 되돌리기

1. 임박 식재료가 있는 오늘의 구조 화면을 연다.
2. 첫 항목을 먹음 처리한다.
3. 완료 Snackbar에서 실행 취소한다.

기대 결과:

- 처리 직후 항목이 구조 큐와 향후 알림에서 빠진다.
- 실행 취소 후 원래 순서와 알림 계획으로 복구된다.
- 빠르게 여러 번 탭해도 소비 이벤트는 한 번만 기록된다.

### `AT-003` OCR 실패 후 직접 입력

1. 품목을 찾을 수 없는 이미지를 공유한다.
2. 실패 화면에서 직접 입력을 선택한다.
3. 이름만 입력하고 날짜 없이 저장한다.

기대 결과:

- 앱이 종료되거나 빈 화면에 머물지 않는다.
- 날짜 없는 항목은 확인 필요 목록에 저장된다.
- 임의의 예상 날짜와 알림을 만들지 않는다.

### `AT-004` 알림 권한 거부 상태

1. 첫 알림 권한 요청을 거부한다.
2. 임박 항목을 만든 뒤 홈으로 이동한다.
3. 홈 배지에서 해당 항목을 처리한다.

기대 결과:

- 권한 거부 때문에 등록·조회·소비 기능이 막히지 않는다.
- 홈 배지가 알림의 핵심 정보를 대신 제공한다.
- 설정에서 권한과 알림 기준을 다시 확인할 수 있다.

### `AT-005` 프로세스 종료 후 초안 복구

1. 공유 분석을 완료하고 선별 결과 일부를 수정한다.
2. 앱 프로세스를 종료한다.
3. 앱을 다시 실행한다.

기대 결과:

- 초안과 현재 단계가 복구된다.
- 사용자가 선택·수정한 값이 자동 분석값으로 되돌아가지 않는다.
- Bitmap 전체를 UI state에 저장하지 않는다.

## 16. 개발 완료 기준

기능 하나를 완료하려면 다음 조건을 모두 충족한다.

- 관련 요구사항과 예외 ID가 이 문서의 테스트 케이스에 연결되어 있다.
- 성공 경로뿐 아니라 빈 상태, 오류, 재시도, 프로세스 복구를 검증한다.
- 순수 비즈니스 규칙은 Android 프레임워크 없이 단위 테스트할 수 있다.
- 버그를 수정할 때는 재현 테스트를 먼저 추가하고 케이스 ID를 남긴다.
- 새 테스트가 로컬에서 통과하고 기존 테스트를 깨뜨리지 않는다.
- UI 변경은 기본 상태·다크 모드·200% 글자 크기 Preview 또는 스크린샷을 확인한다.
- 자동화하지 못한 항목은 이유와 수동 검증 결과를 기록한다.
- 테스트를 비활성화하거나 flaky로 분류할 때 추적 이슈 없이 방치하지 않는다.

## 17. 테스트 코드 작성 규칙

```text
테스트 함수: given_<조건>_when_<행동>_then_<결과>
테스트 클래스: <대상 이름>Test
계측 테스트: <화면 또는 흐름 이름>InstrumentedTest
Compose 테스트: <화면 이름>ScreenTest
```

- 한 테스트는 사용자가 이해할 수 있는 행동 하나를 검증한다.
- 시간은 `Clock`, ID는 생성기, 외부 분석기는 인터페이스로 주입해 재현 가능하게 만든다.
- 테스트끼리 실행 순서와 실제 현재 시간에 의존하지 않는다.
- fixture에는 실제 영수증·주소·카드번호 등 개인정보를 사용하지 않는다.
- 테스트 이름 또는 `@DisplayName`에 테스트 케이스 ID를 포함한다.
- 구현이 시작되면 `PLANNED`를 `AUTOMATED` 또는 `MANUAL`로 갱신한다.
